# Private native crash observer

`capture_crash_stack` remains default off. An explicit diagnostic dispatch builds a private corrected GDB 17.2 and must pass all four real Windows preflight cases before attaching it to an already-owned installed InkQuay process. This changes no product binary, feature, qualification acceptance, signal/input policy or lifecycle requirement. No debugger binary is uploaded or installed over the recorded toolchain.

The observed MSYS2 GDB 17.2-1 passed symbolized SIGSEGV delivery and normal detach, but an abrupt debugger exit killed the owned fixture with `0xc0000354` (`STATUS_DEBUGGER_INACTIVE`). In [GNU's 17.2 attach source](https://gnu.googlesource.com/binutils-gdb/+/refs/tags/gdb-17.2-release/gdb/windows-nat.c), `DebugActiveProcess` runs inside `do_synchronously`, on the Windows debug-event worker; `DebugSetProcessKillOnExit(FALSE)` was called outside that worker. [Microsoft documents](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-debugsetprocesskillonexit) that the latter must run on the thread that established the debug connection. Calling it from an external Python process or GDB's main Python thread would not repair this boundary.

`gdb-17.2-worker-kill-on-exit.patch` moves the policy call into the successful attach worker. It checks the native result and attempts immediate detach on policy-setting failure, then returns the actual attach error. It otherwise preserves the native attach implementation. The source preimage and result are separately hash-pinned. All existing signal-pass, normal-detach, abrupt-debugger-exit and timeout-detach preflight cases remain required; a failed or partial case cannot authorize attachment.

The separately downloaded source and this GNU GDB derivative are **GPL-3.0-or-later**. Original GNU copyright/license headers and `COPYING3` remain in the private extracted source tree. The source URL, exact hash, license-file hash, patch/helper hashes, compiler/linker/build-tool hashes, recorded native package/version hashes and final tool/runtime DLL hashes are retained in `build-evidence/crash-observer-tool.json`. The local orchestration scripts are MIT licensed; this does not change GNU GDB's license.

- Private output: `build-observer-gdb/build/gdb/gdb.exe`. Its actual hash is determined by the current Windows build and verified again before the fixture and production observation. The tool's recorded MINGW64 runtime DLL directory is added only to the debugger child's environment.

The build reuses the already-recorded MINGW64 GCC/G++, binutils, GMP, MPFR, Expat, iconv, zlib, xz, zstd and xxHash dependencies, plus MSYS bash/make/coreutils. It builds only native x64 GDB with two jobs and `-O1 -g0`; Python, Guile, debuginfod, TUI, source highlighting, simulator, gdbserver and other binutils programs are disabled. There is no cache or package installation. Configure is limited to five minutes and make to twenty, with ten-second forced termination grace. The step is capped at 27 minutes and only the diagnostic job budget extends to 90 minutes. Actual Windows build duration and success are not established locally.

Build failures retain bounded configure/make tails and keep attachment disabled. The ordinary consumer workflow still runs and retains its own primary outcome. The uploaded metadata globs include the build receipt but exclude `build-observer-gdb`, source archives and executables. The private source/tool tree is left only on the ephemeral runner for the duration of that job.

Bundled gdbserver was considered and rejected for this task: although its attach policy runs on the proper thread, GDB 17.2's native Windows transport rejects stdio and forces TCP listeners to all interfaces. No new listener, debugger-thread injection, inferior function call or relaxed target-survival check is introduced here.
